Remote Access Is a Convenience; the Restaurant LAN Is the Fallback

Cloudflare’s November 2025 postmortem described a global failure to deliver core network traffic. For a restaurant system, a tunnel can help remote access but should not be confused with the local service.

By Raktim Ranjit · Updated 27 October 2026 · 4 min read

The incident, and the operational question

A tunnel or reverse proxy can make a local service reachable from outside, but it adds another provider and network path. When that layer is down, remote owners may lose access even while staff on the restaurant Wi-Fi can still work. That separation should be rehearsed instead of discovered during dinner service.

What the primary record says

Cloudflare’s 18 November 2025 postmortem says a database-permission change caused its Bot Management feature file to contain duplicate entries and grow beyond the limit expected by software on its network. The bad file propagated globally, and core traffic began failing at 11:20 UTC. Cloudflare says it stopped propagation and restored a known-good file; core traffic was largely flowing by 14:30, with the long tail of recovery ending around 17:06. The postmortem also describes related effects on Turnstile, Workers KV, Access and dashboard logins. Cloudflare stated that the event was not caused by a cyberattack.

What this means for a working business

A tunnel is a path for remote access, not a guarantee that the application is reachable from every network condition. If staff devices and the local server are on the same LAN, local traffic may still work when the internet-facing tunnel or edge service fails. Remote managers may lose their path at the same time. The distinction only helps when the local URL, staff permissions and printers are configured in advance; discovering them during dinner service is not a fallback. It is also important to avoid exposing an unauthenticated admin screen as a quick workaround.

Where the product fits in the actual workflow

OrderRestro documents local-LAN operation and optional remote access through tunnel or reverse-proxy arrangements. This allows a restaurant to plan the service path for staff on site separately from an owner’s remote dashboard. A Cloudflare outage does not automatically imply the local app fails, and a local installation does not guarantee every external integration continues. The actual result depends on where the app runs, how DNS and identity are configured, and which functions the restaurant has tested. Keep the remote route protected and treat it as an additional dependency, not the only route.

Walk through a realistic failure

Imagine the remote tunnel stops resolving during service. The manager outside the restaurant may lose access, but a staff tablet on the restaurant Wi-Fi could still reach a LAN-hosted app directly. Test both paths separately and make the local address easy for staff to find. If local operations work, leave security settings intact and keep taking orders on that route; do not expose an admin port publicly to restore remote convenience. After the tunnel returns, confirm that remote dashboards show the same orders staff created locally. Define who checks for synchronization gaps and how the owner gets notified if the external route stays down.

A practical continuity drill

Run this during a quiet period with the person who will make the decision during a real incident. Write down what you observe, what is unavailable, and how staff return to normal operation. A drill that ends with a clear owner and a measured recovery time is more useful than a checklist nobody has tried.

  • Write down the LAN address staff use and the separate public address used for remote access.
  • Test local ordering and printing with the internet disconnected; test remote access separately.
  • Define how administrators will communicate if the tunnel, DNS or identity provider is unavailable.
  • Do not weaken authentication to restore remote access; use a documented secure alternative.

Questions to answer before relying on the setup

  • Can staff reach the server by its local address without public DNS?
  • Which features rely on Cloudflare or another edge provider?
  • How will the owner receive incident updates if the dashboard login is down?
  • Is remote access disabled safely when it is not needed?

Scope and limitations

A tunnel does not make the app immune to a Cloudflare incident, and local operation does not guarantee that every integration or payment provider works offline.

Product documentation to verify before deployment

OrderRestro’s public docs describe both a local-LAN deployment and optional tunnel or reverse-proxy access. The local setup is the natural continuity path for tables, billing, KDS, and printers. Remote access should be treated as a separate capability with its own failure mode.
