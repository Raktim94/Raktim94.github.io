The Outage After the Outage: Can You Still Rebuild Your Software?

Docker reported that its October 2025 services were affected by the AWS US-EAST-1 event. It shows why recovery depends on deployment artifacts as well as running servers.

By Raktim Ranjit · Updated 27 October 2026 · 4 min read

The incident, and the operational question

A service can keep running while its image registry, build system, or deployment control plane is unavailable. Later, a failed host or rollback can turn that secondary dependency into the next outage. A realistic continuity plan asks whether you have pinned images, a copy of required artifacts, and a written path to rebuild.

What the primary record says

Docker’s incident report says the 20 October 2025 AWS US-East-1 disruption affected Docker Hub, Hardened Images, Scout, Build Cloud, Automated Builds and Testcontainers Cloud. Docker describes increasing failures from 06:48 UTC, broad service unavailability from 08:01 UTC and a staggered recovery; some services were restored on 20 October while Automated Builds recovered the following morning. This is a valuable distinction: a running application can keep serving traffic while its image registry or build service is unavailable, but a replacement, rollback or fresh installation may then be harder to perform. The report also discusses Docker’s planned work on caching and multi-region reads.

What this means for a working business

Deployment readiness includes the artifacts and instructions required to recreate a service, not only the machine that is currently running it. A team should know the exact image tag in production, where that image can be retrieved, which configuration is required, and whether the data volume is separate from the replaceable application container. Pinning versions reduces surprise but does not remove the need to retrieve the pinned artifact. A backup of application data is not a copy of the image, and a registry mirror is not a backup of the database.

Where the product fits in the actual workflow

NodeDR POS publishes Docker Compose installation paths, and its documentation describes an updater designed to replace application containers without touching the data volume. That separation is useful only when the operator understands the volume mapping, image version and backup process in the actual installation. The public repository is the source for the current deployment instructions; this article does not claim that every user has a local image mirror or can rebuild the app without internet access. Test the recovery path on a spare machine before depending on it at the counter.

Walk through a realistic failure

Consider a till whose container is healthy when the registry goes offline. Customers may still be served for a while, so avoid unnecessary restarts. If the host then fails, staff need a copy of the exact application image, environment configuration and database backup to recover. The operator should know where those artifacts are stored, who can access them, and how to verify the restore without overwriting production data. Test on a spare machine, including printers, scanner input and local-network access. A successful container start is not enough if the shop cannot bill, print or safely reconcile the day’s transactions.

A practical continuity drill

Run this during a quiet period with the person who will make the decision during a real incident. Write down what you observe, what is unavailable, and how staff return to normal operation. A drill that ends with a clear owner and a measured recovery time is more useful than a checklist nobody has tried.

  • Record the image tag and configuration for the installed release; avoid ‘latest’ in a recovery procedure.
  • On a spare host, test whether the exact image can be pulled and started without touching production data.
  • Store database backups and deployment notes in a failure domain separate from the running machine.
  • Check the rollback steps after an update and identify who can authorize a restore.

Questions to answer before relying on the setup

  • Can you name the exact version currently running?
  • Can you retrieve or rebuild that version during a registry outage?
  • Is business data stored separately from the replaceable container?
  • Have you tested the whole restore, including printer and barcode configuration?

Scope and limitations

The project does not claim that every user has a private image mirror or air-gapped rebuild. The operator must confirm the exact deployed version and make backups independently.

Product documentation to verify before deployment

NodeDR POS publishes Docker-based installation paths and documents an updater that swaps app containers without touching the data volume. Operators should understand how their own registry access, image tags, configuration, and backups behave before an incident; keeping a recovery checklist is part of self-hosting.
