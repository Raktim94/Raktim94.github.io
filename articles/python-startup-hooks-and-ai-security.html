Why “We Never Imported That Library” Is Not a Complete Defense

In the October 2026 LiteLLM incident, Microsoft reported that affected Python package files could execute during interpreter startup, rather than waiting for an explicit import.

By Raktim Ranjit · Updated 27 October 2026 · 4 min read

The incident, and the operational question

This is why dependency review must consider runtime behavior and installed artifacts, not just the visible lines in an application. Build isolation, lockfiles, package provenance, least-privilege secrets, and a documented response plan all help teams investigate quickly when an upstream package is compromised.

What the primary record says

Microsoft’s October 2026 analysis of LiteLLM 1.107.0 described malicious .pth and sitecustomize.py files placed in Python’s site-packages. Python can load certain startup customization files when an interpreter starts, so this technique can execute before application code explicitly imports a named library. CERT-In’s advisory independently warns that the reported package compromise could expose secrets available to the affected process, while emphasizing that impact depends on installation, execution and permissions. The distinction is practical: checking whether a project imports a suspect module may be insufficient if a compromised dependency added interpreter-level startup code.

What this means for a working business

Incident response for a package compromise starts with the environment that installed or executed the artifact. Inspect lockfiles, package caches, container layers and deployment timestamps; compare the installed files with a trusted release; and examine where process credentials could travel. Do not copy secrets off a suspect machine to ‘check’ them. Rotate reachable credentials from a clean system, follow vendor guidance and preserve logs if compromise is plausible. For teams, least privilege limits the difference between an infected build runner and a compromised production fleet.

Where the product fits in the actual workflow

KinetiRx uses a Go backend and React frontend according to its public repository, while optional AI functions can bring Python-based services or external SDKs into an operator’s broader environment. The exact installation path matters; this incident is not evidence that KinetiRx itself used the compromised LiteLLM package. Its lesson is to inventory every component around a product, including optional services, OCR tools, containers and build runners. Keep optional integrations separate and do not give them blanket access to the pharmacy database or host credentials.

Walk through a realistic failure

Treat the build machine as part of the incident when a Python package may have installed startup hooks. Inventory the interpreter and environment that executed installation, compare `.pth` and `sitecustomize.py` files with trusted package contents, and check logs for network activity and credential access. Rebuild into a clean environment from reviewed artifacts instead of trying to sanitize a machine whose trust is uncertain. Keep the affected runner from publishing new builds until it is cleared. If the process had access to API keys or cloud tokens, rotate them from a clean device and check use history after rotation.

A practical continuity drill

Run this during a quiet period with the person who will make the decision during a real incident. Write down what you observe, what is unavailable, and how staff return to normal operation. A drill that ends with a clear owner and a measured recovery time is more useful than a checklist nobody has tried.

  • Rebuild from a clean, known-good image rather than trusting an environment that may have executed a startup hook.
  • Review `.pth`, `sitecustomize.py` and package inventories against vendor-provided indicators and timelines.
  • Use locked dependency files and controlled artifact promotion from test to production.
  • Keep CI tokens short-lived and grant publish permissions only to the job that needs them.

Questions to answer before relying on the setup

  • What ran on the host during the affected release window?
  • Can the app be rebuilt without reusing possibly tainted caches?
  • Are deployment and package publishing credentials separated?
  • Is there a written process for rotating a key from a clean workstation?

Scope and limitations

The KinetiRx project is not a software supply-chain security product. The incident is a prompt to inspect dependencies and credentials; it is not proof that any specific KinetiRx release was affected.

Product documentation to verify before deployment

KinetiRx’s AI-assisted bill OCR is optional, and the README distinguishes ordinary operation from the Gemini key path. A pharmacy can decide whether to configure that integration and should scope its key and data flow before enabling it.
