FIELD NOTE 17 · ORDERRESTRO

One Malicious npm Package Can Reach Far Beyond the App That Uses It

Singapore’s Cyber Security Agency describes the 2025 Shai-Hulud campaign, in which compromised npm packages could search developer systems for credentials and propagate through package releases.

By Raktim Ranjit · Updated 27 October 2026 · 4 min read

The incident, and the operational question

A business choosing self-hosted open-source software should look beyond the license: how are releases built, how are dependencies tracked, and where do security notices appear? Maintainers also need to protect their own accounts and publish a response path.

What the primary record says

Singapore’s Cyber Security Agency advisory on the 2025 Shai-Hulud npm campaign describes compromised packages with a self-propagating payload. The agency says the malware could search developer systems for credentials, validate them, create unauthorized GitHub Actions workflows and exfiltrate secrets. Its advisory explains why transitive dependencies matter: a project may install a compromised package through another package, and a CI workflow may run it during a build. The campaign affected many packages, but a broad advisory is not evidence that a particular repository or product was compromised. Investigations must use the affected-package lists and timelines published by trusted responders.

What this means for a working business

Open source makes code available for inspection; it does not guarantee that every published version is safe or that every maintainer account is protected. Reproducible builds, lockfiles, review of dependency changes and controlled release processes reduce surprise. CI should receive only the permissions it needs for the job at hand. Secrets should not be exposed to untrusted pull-request code, and build artifacts should be promoted only after checks pass. Teams should know how to identify the exact package versions that were installed rather than trying to remember which libraries a developer intended to use.

Where the product fits in the actual workflow

OrderRestro’s repository is public and its README documents its stack and deployment path, including TypeScript, NestJS, Next.js, Node and pnpm. Visibility lets operators inspect the project and its dependency manifests; it does not certify the release pipeline or remove transitive package risk. Before deploying, check the current lockfile, security notices and documented install process. Keep API keys and production data out of the repository, and update from trusted releases after reviewing project guidance.

Walk through a realistic failure

Suppose a developer machine installed a compromised transitive npm package during a build. First find the exact lockfile and artifact versions; then establish whether the install ran on a laptop, CI runner or production host. The credentials available to each environment determine the possible scope. Do not assume that a clean-looking app bundle proves no compromise, and do not rotate secrets from the potentially affected host. Follow the current official advisory, preserve useful logs and rebuild from a clean environment. A maintainer should also review who can publish releases and whether untrusted pull requests can reach repository secrets.

A practical continuity drill

Run this during a quiet period with the person who will make the decision during a real incident. Write down what you observe, what is unavailable, and how staff return to normal operation. A drill that ends with a clear owner and a measured recovery time is more useful than a checklist nobody has tried.

  • Search lockfiles and build artifacts for versions named in the current official advisory.
  • If a host ran an affected package, preserve relevant logs and follow trusted incident-response guidance before rotating secrets.
  • Pin dependencies and review lockfile changes as part of code review.
  • Restrict CI tokens and separate untrusted tests from jobs allowed to publish releases.

Questions to answer before relying on the setup

  • Can you identify the exact dependencies installed in production?
  • What permissions does the build workflow receive from GitHub?
  • Can an untrusted pull request access a publishing token?
  • Who reviews security advisories and decides when to update?

Scope and limitations

Open source does not mean audited, risk-free, or automatically updated. Pin and review dependencies, protect backups, and apply security updates through a process you understand.
